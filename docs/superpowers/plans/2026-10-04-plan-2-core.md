# Plan 2 — `rdm-core`: download manager (headless)

> Executed inline (superpowers:executing-plans). **Compact format by ruling:** the user asked to cut token
> usage, and the executor is the plan's author in the same session. So this plan pins interfaces,
> behaviour and every test, but leaves implementation bodies out instead of spelling out code twice.

**Goal:** a headless `Manager` that owns all downloads, queues, schedule, speed limit and settings, persists
to `state.json`, and streams `Event`s. The basic UI (Plan 5) and the Figma UI only talk to this.

**Spec:** `docs/superpowers/specs/2026-10-03-rdm-design.md` §2.3, §3, §4, §7 · **Branch:** `feat/core` (from `feat/engine`)

## Global constraints
- Crate `crates/core`, package `rdm-core`, which depends on `rdm-engine`. It has no UI dependencies and no yt-dlp (that's Plan 3).
- Local time comes from `chrono` (`default-features = false, features = ["clock"]`).
- Tests need no internet and use their own small axum server in `crates/core/tests/support/mod.rs`.
- Every state change emits an `Event`. Persistence is debounced: at most one save per second, plus one on shutdown.

## Interfaces (`rdm_core::…`)
```rust
pub struct ItemId(pub u64);                       // Copy, Eq, Hash, Ord, serde
pub type QueueId = u32;                           // 0 = "Main", always active
pub enum Status { Queued, Running, Paused, Done, Failed(String) }
pub enum Category { Video, Music, Archive, Document, Program, Other }
impl Category { pub fn from_name(file_name: &str) -> Self; pub fn folder(self) -> &'static str }
pub struct Item { id, url, name, category, status, dest: Option<PathBuf>, downloaded: u64,
                  total: Option<u64>, #[serde(skip)] speed_bps: u64, queue: QueueId, added: i64 }
pub struct Schedule { start: u16 /*min of day*/, stop: Option<u16>, days: [bool; 7] /*Mon..Sun*/ }
impl Schedule { pub fn is_active(&self, now: Now) -> bool }  // supports overnight windows
pub struct Queue { id, name, max_concurrent: usize, schedule: Option<Schedule> }
pub struct Settings { download_dir, sort_into_folders, connections, max_concurrent,
                      speed_limit_bps, accent, clipboard_watch, start_immediately }  // Default
pub struct AppState { next_id: u64, items: Vec<Item>, queues: Vec<Queue>, settings: Settings } // Default
pub struct Now { weekday: u8 /*0=Mon*/, minute: u16 }  impl Now { pub fn local() -> Self }
pub fn pick_next(state: &AppState, running: &HashSet<ItemId>, now: Now) -> Vec<ItemId>;
pub mod store { pub fn load(path) -> AppState; pub fn save(path, &AppState) -> io::Result<()> }
pub enum Event { Added(Item), Updated(Item), Removed(ItemId), Settings(Settings) }
#[derive(Clone)] pub struct Manager;
impl Manager {
  pub fn start(state_path: PathBuf) -> Manager;           // spawns the actor on the current runtime
  pub fn subscribe(&self) -> broadcast::Receiver<Event>;
  pub async fn snapshot(&self) -> AppState;
  pub async fn add(&self, url: String) -> ItemId;
  pub async fn pause(&self, id: ItemId); pub async fn resume(&self, id: ItemId);
  pub async fn remove(&self, id: ItemId, delete_file: bool);
  pub async fn update_settings(&self, s: Settings);
  pub async fn shutdown(&self);                           // pauses running items, saves
}
```

## Behaviour
- **add:** the name is guessed from the URL and the category from the name. The status is `Queued` if `start_immediately` is set, otherwise `Paused`. Emits `Added`, then runs the planner.
- **Start an item:** probe → real name and category → `dir = download_dir[/category.folder()]` → `dest = filename::resume_target(dir, name, url)` (an item that already has a `dest` keeps it) → `engine::download` with the shared `RateLimiter` and `connections` from settings. Progress is forwarded every 250 ms as `Updated`.
- **Finish:** `Completed` → `Done`. `Paused` → `Paused`, or `Queued` if it was stopped by its schedule. `Err` → `Failed(msg)`. Each case emits `Updated`, then the planner runs again.
- **pause:** a running item is cancelled; a queued one becomes `Paused` at once. **resume:** `Paused` or `Failed` → `Queued`.
- **remove:** a running item is cancelled first. Afterwards its `.rdmpart`/`.rdmstate` are deleted, plus `dest` if `delete_file` is set. Emits `Removed`.
- **Planner:** takes `Queued` items first-in-first-out whose queue is active and not full, until `settings.max_concurrent` is reached. Running items whose queue becomes inactive are stopped and go back to `Queued`.
- **Settings:** stored; `limiter.set_limit(speed_limit_bps)`; emits `Settings`; the planner runs again.
- **Load:** `Running` → `Paused`, `speed_bps` = 0. A missing or corrupt file → `AppState::default()`.

## Review focus
1. Shutdown while downloads run: every running item must end up `Paused` in `state.json`, never `Running`.
2. Removing an item while it's starting (still probing): it must not come back as a ghost when its task finishes. → `remove_deletes_partial_files` removes right after `Running`.
3. Two items with the same URL: they get different destinations (`name`, `name (1)`), because the engine refuses a shared destination.
4. Settings change mid-download: the new speed limit applies live through the shared limiter; the new connection count applies only to newly started items.
5. Event channel lag: a slow UI subscriber gets `Lagged`, and `snapshot()` must always recover the full state.
